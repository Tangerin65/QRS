## 打开和审阅

首次拉取后，将 mini-program/project.config.example.json 复制为同目录下的 project.config.json，填入团队确认的小程序 AppID，再用微信开发者工具导入 mini-program 文件夹。已有本地配置可继续使用。project.config.json 和 project.private.config.json 均仅在本机保留，不提交 Git。

config/index.js 中 baseUrl 留空时仅展示公共页面；不会伪造认证成功。访客只能看到首页、我的与绑定入口，业务菜单隐藏。填写 HTTPS 地址后，首页或个人中心用新的 wx.login code 请求后端识别绑定关系。

退出后保存的只有“已主动退出”标志，阻止自动重新登录；用户点击“微信登录”才恢复登录。Token、OpenID、二维码票据、档案数据都不写入本地存储。初版 records_session 缓存会在启动时清除。

## 成员 6 需要提供的接口

所有返回采用 JSON：成功 code 为 200 或 0，业务数据位于 data；错误 code 使用下方错误码。服务端必须对每个业务请求校验用户状态、绑定关系和数据权限。前端隐藏入口不能替代服务端授权。

| 方法与路径 | 请求 | data 返回与用途 |
| --- | --- | --- |
| POST /api/mobile/auth/login | code（wx.login 临时凭证） | 未绑定时 {bound:false}；已绑定时返回会话对象 |
| GET /api/mobile/auth/session | Bearer Token | 会话对象；停用、解绑、过期时拒绝；需返回最新权限 |
| POST /api/mobile/auth/logout | Bearer Token | 撤销该 Token；成功 data 可为 null |
| POST /api/mobile/account/bind | code、userNo（均为字符串） | 完成首次绑定后返回会话对象 |
| POST /api/mobile/auth/pc/inspect | ticket、Bearer Token | 待确认登录信息，见下文 |
| POST /api/mobile/auth/pc/confirm | ticket、Bearer Token | {state:"confirmed"} |
| POST /api/mobile/auth/pc/cancel | ticket、Bearer Token | {state:"cancelled"} |

会话对象示例（仅展示协议字段）：

~~~json
{
  "token": "<服务端签发的令牌>",
  "userId": "3",
  "userName": "ZhaoBoyu",
  "roleName": "普通用户",
  "permissions": ["records:search:view", "records:message:view"]
}
~~~

GET session 可省略 token，前端沿用当前令牌。首次登录或绑定必须返回 token。权限数组缺失时默认没有任何业务权限；角色名称不直接授予权限。records:search:view 对应查档，records:message:view 对应消息。明确返回 *:*:* 才代表全部功能权限。这里的权限名必须与成员 1 的 M13、成员 4 的 M16、成员 6 的 M12 协商；如团队选择其他名称，只在 utils/navigation.js 中统一修改。

错误处理支持 HTTP/业务 401、403、404、409、410、429；字符串错误码支持 ACCOUNT_UNBOUND、ACCOUNT_DISABLED、ALREADY_BOUND、QR_EXPIRED、QR_USED、INVALID_QR。401、停用或解绑立即清理旧会话、移除业务入口。403 只拒绝本次操作。服务端异常不把原始堆栈转给用户。不得将停用账号映射为成功或普通未绑定。

## 绑定二维码

按需求支持纯文本用户编号，例如 0003。编号不转数字，因此不会丢失前导零和长整数精度。也兼容 {type:"bind",userNo:"0003"} JSON；JSON 中 userNo 必须为字符串。允许字母、数字、下划线、连字符，长度 1–64。若团队编号规范不同，需要同步调整 utils/qr.js。

前端仅把微信临时 code 与 userNo 提交后端，由后端换取 OpenID 并完成绑定。微信 AppSecret 不能进入小程序。已有绑定不得在前端直接覆盖；由管理员在后台解除旧绑定后重新绑定。绑定接口必须检查编号有效性、账号状态、已有绑定，并遵循团队确认的首次绑定授权流程。

## 电脑登录二维码

建议二维码内容：

~~~json
{"type":"pc-login","ticket":"<24至256位随机base64url凭证>"}
~~~

纯用户编号不能用于电脑登录。票据放在页面实例内存中，不出现在 setData、存储、日志或页面 URL。二维码内容不包含账号和个人资料。前端只向配置好的固定 HTTPS 接口请求，不根据二维码中的 URL 访问外部站点。

inspect data 必须返回：

~~~json
{
  "state": "pending",
  "deviceName": "Windows / Chrome",
  "location": "服务端识别的登录位置",
  "serverTime": 1794700000000,
  "expiresAt": 1794700120000
}
~~~

时间为毫秒时间戳或带时区的 ISO 8601 字符串。前端根据 expiresAt 与 serverTime 的差值倒计时，避免直接依赖手机时钟。设备、位置由后端提供，仅用于用户核对。服务端在 inspect、confirm、cancel 时都必须校验认证、二维码有效期、状态和关联的电脑请求；确认时必须原子地消费一次性票据，取消后不能再确认。

小程序扫描后只展示待确认信息，不自动登录电脑。用户明确选择“确认登录”或“拒绝登录”才发送写入操作；按钮提交中锁定。网络失败不显示成功、不自动重复提交，提示核对电脑端后刷新二维码重扫。

## 其他成员如何接入页面

- 从 utils/navigation.js 统一登记业务入口和权限，不根据角色昵称猜测权限。
- 从 utils/request.js 发请求；Promise 返回 data，错误为含 code、statusCode 的 Error。
- pages/archives 与 pages/messages 已示范页面入口权限校验。接入真实页面时，权限撤销或退出后还需清理该业务页数据和取消正在进行的请求。
- components/request-state 支持 loading、error、empty，retry 事件由调用页明确处理；写入操作不自动重发。
- pages/profile 目前只承载公共登录管理。成员 6 在此接入头像、基础资料、个人工作台和统计；不要创建第二套登录状态。
- 不缓存敏感档案或无权访问的数据；本次未实现业务草稿存储，各模块如需要非敏感草稿需另行定义字段白名单、所属用户和恢复提示。
- 业务请求仍由后端逐次鉴权，前端入口检查不能提供真正的数据访问控制。
